# hermes-context-rules

Cursor- and Claude-compatible conditional project rules for Hermes Agent.

Single source of truth: `.cursor/rules/*.mdc` (Cursor format: frontmatter
`description` / `globs` / `alwaysApply`). Cursor reads them natively; this
plugin gives Hermes the same conditional semantics — plus something neither
Cursor nor Claude Code has: **deterministic enforcement**.

## The problem it solves

- `AGENTS.md` loads in full, always, unconditionally — and the model may
  ignore it: it is advisory prose.
- Describing deterministic checks (linters, gates) bloats AGENTS.md, even
  though that logic is code, not prose.

## What the plugin does

| Rule type (frontmatter) | Behavior in Hermes |
|---|---|
| `alwaysApply: true` | Full text into the system prompt (section `context.rules.manifest`, rendered per session cwd) |
| `globs: src/**/*.py` | Auto-inject the full text into the result of the first tool call touching a matching file (read_file / write_file / patch / search_files / terminal workdir). Later touches — one-line reminder only |
| `description:` (no globs) | Compact index in the prompt: name + description + path; the agent reads the file on demand |
| none (manual) | Only via `/context-rules show <name>` |
| `enforce: <shell cmd>` (extension; Cursor ignores it) | Gate: the command runs at `pre_verify` over the turn's changed files matching `globs`. Non-zero exit → the agent must fix it (the turn does not finish). Analogous to a Claude Code Stop-hook, a generalization of text_lint_gate |

Rule files may change during a session: the cache invalidates by mtime.

## .mdc format

```markdown
---
description: Python style for this repo
globs: ["src/**/*.py", "tests/**/*.py"]
alwaysApply: false
enforce: .venv/bin/python -m ruff check --no-cache $RULE_FILES
---

No wildcard imports. Type hints on all public functions.
```

Fields:
- `description`, `globs` (comma string or list), `alwaysApply` — as in Cursor.
- `enforce` — optional extension: a shell command. Runs with cwd = the rule
  root; changed files are passed both as arguments and via env `RULE_FILES`
  (newline-separated) and `RULE_ROOT`. Timeout 120 s.

Sources (in priority order): `.cursor/rules/*.mdc`, then `.claude/rules/*.md`
(frontmatter optional; without it the rule counts as `alwaysApply: true` —
matching Claude Code's own behavior). Files generated by `/context-rules sync`
are skipped when reading.

When a project has both sources, everything found is merged into one pool —
there is no "first source wins" shadowing (unlike Hermes' built-in handling of
CLAUDE.md vs AGENTS.md). Cursor rules are listed first; name collisions
between the two sources coexist as distinct rules (key = root|source|name).

## Claude Code compatibility

```
/context-rules sync
```

Generates `.claude/rules/<name>.md` from each `.mdc` (every mode): frontmatter
stripped, body plus a header line noting when to apply ("apply when working
with files matching <globs>" for glob rules; mode-appropriate notes
otherwise). Claude Code loads them flat (it has no conditionality); Hermes
loads them conditionally through this plugin. The roundtrip is safe:
generated files carry a marker comment and are skipped when reading, so a
rule is never counted twice. Handwritten (unmarked) `.claude/rules/*.md`
files are never overwritten by sync — name collisions between the two
sources coexist as distinct rules.

## Sync targets

The canon is `.cursor/rules/*.mdc`; sync materializes it into consumer
locations:

| Target | Writes | Notes |
|---|---|---|
| `claude` (default) | `.claude/rules/<name>.md` | Claude Code compat, as above |
| `zcode` | `.zcode/rules/<name>.md` **plus** a digest block in the workspace `AGENTS.md` | For the zcode client, which has no auto-load of `.zcode/rules/` |
| `all` | both of the above | Claude target first, then zcode; the report has one labeled section per target |

```
/context-rules sync --target zcode
/context-rules sync --target all
```

No flag means `claude` — exactly the pre-change behavior: nothing is ever
written to `.zcode/` or `AGENTS.md` without the explicit flag.

The zcode digest block sits between `<!-- BEGIN:RULE-DIGESTS -->` and
`<!-- END:RULE-DIGESTS -->` markers in `<root>/AGENTS.md` — one
`- **<name>** — <summary>` line per rule (the `description` frontmatter when
present, otherwise a mode/glob apply-note), sorted by rule name. Sync
rewrites **only the lines strictly between the markers**; every other byte of
AGENTS.md is yours. Missing AGENTS.md is created with a `# Project rules`
heading plus the block; zero rules leaves the markers with the lines cleared;
a malformed block (a missing or doubled marker) is reported as skipped and
never auto-repaired.

Invariants, identical for both targets:

- `.cursor/rules/*.mdc` stays the single source of truth; edit the `.mdc`,
  never the projection.
- Generated projections carry the same generated-marker header for both
  targets and are skipped when rules are read.
- `.zcode/rules/` is **never a rule source** for this plugin — discovery
  reads only `.cursor/rules` and `.claude/rules`.
- Handwritten (unmarked) files in `.claude/rules/` or `.zcode/rules/` are
  never overwritten or removed; a name collision is reported as skipped.
- A generated projection whose canon `.mdc` is deleted is pruned on the next
  sync (and its digest line dropped).

Commit or ignore advice: `.zcode/rules/` and the AGENTS.md digest block are
deterministic outputs of the canon — commit them (like `.claude/rules/`) so
teammates and CI see the same projections, or add `.zcode/` to `.gitignore`
and let each workspace regenerate on demand. Do not hand-edit between the
digest markers.

## Commands

- `/context-rules status` — rules found for the session cwd, by mode
- `/context-rules list` — names only
- `/context-rules show <name>` — full text of one rule
- `/context-rules sync [--target claude|zcode|all]` — regenerate flat
  projections from the canon (default `claude`: `.claude/rules/*.md` only;
  `zcode`/`all` also write `.zcode/rules/*.md` + the AGENTS.md digest block)
- `/context-rules sync-from-claude` — import handwritten `.claude/rules/*.md`
  into `.cursor/rules/*.mdc` (the canon). Two phases: bare `sync-from-claude`
  is a read-only plan (`ready` / `ask` / `conflict` / `imported` per rule);
  `sync-from-claude apply <name> [always | glob <globs...> | desc <text...> |
  manual] [--force] [--as <new-name>] [--root <dir>]` writes one `.mdc` with
  the body copied verbatim and rewrites the source `.md` in place as a
  generated projection, so `.cursor` becomes the single source of truth.
- `/context-rules verify` — explanation of how enforce gates run

## Installation

Drop or symlink the plugin directory into `$HERMES_HOME/plugins/context-rules/`
(or `~/.hermes/plugins/context-rules`) and enable it:

```
ln -s ~/Projects/hermes-context-rules ~/.hermes/plugins/context-rules
hermes plugins enable context-rules
```

It is picked up at the next Hermes start. Dependencies: stdlib only; PyYAML
is optional (a frontmatter fallback parser is built in).

Uses only documented plugin surfaces:
`register_middleware("tool_execution")`, `register_hook("post_tool_call")`,
`register_hook("pre_verify")`, `register_system_prompt_section`,
`register_command`.

## Prompt-cache safety

- The system-prompt section is rendered once per session and frozen by Hermes
  (plugin sections are snapshot-cached), so the cached prefix stays
  byte-identical turn over turn.
- Glob-rule injections append to NEW tool results only; past messages are
  never rewritten — no cache invalidation, just bounded context growth
  (full text once per rule per session, then one-line reminders).
- The pre_verify gate only emits a message on failure, appended as a new
  message — again, no history rewrite.

## Limitations (MVP)

- Paths inside `terminal` commands are not parsed — only `workdir` (parsing
  command bodies is noisy and unreliable).
- Relative paths in tool args resolve against the Hermes process `os.getcwd()`.
- Full-text injection happens once per session; if rule files change mid-session,
  the prompt index does not refresh (the price of prompt caching). Fresh bodies
  still arrive via injections for newly touched files.
